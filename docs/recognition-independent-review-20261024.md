## 结论

**同步阻塞可由代码确认，但现有日志不能确认它就是用户“卡片出现后慢”的具体原因。按钮/卡框检测是值得验证的减少无效 OCR 方案，不是已经证明的延迟修复。PR #15 继续保留草稿，不宜直接以识别速度修复合入。**

### 已确认：整块调用会暂停同一识别线程的新画面检查

`lolhex/engine.py:112-115` 只启动一个 vision 线程；`:540` 标题检查、`:547` 整块调用与 `:582` 的 `det.scan_full` 均在这条线程顺序执行。1.1.1 对照代码同样直接同步调用 `scan_full`。调用完成前不能开始下一次标题截图；这不等于整个 GUI 或游戏被阻塞。

应纠正“手动重扫立即触发”的宽泛说法：手动事件能绕过自动预算，但不能中断已经执行的 OCR。现有循环测试证明循环有机会处理事件时绕过冷却，没有证明在途推理能被抢占。

### 已确认：原始日志有显著整块耗时，未记录真实选卡出现时刻

直接重读 16:22:33 快照中的 gzip，按 1.1.1 启动版本分段：本轮 116 份上传，112 台有整块扫描计时；23 台至少一局的整块扫描平均值 >5 秒，6 台 >10 秒。一次慢对局记录 21 次整块扫描，平均 21742 毫秒、当前线程 CPU 平均 21261 毫秒，同局标题条平均 196 毫秒。

这是每局汇总，不是逐次推理耗时，更不是“选卡出现到推荐显示”的时长。标题统计也不包括等待前一个整块调用的时间，不能拿 196 毫秒当作玩家体验延迟。CPU 时间接近墙钟说明该例有实际计算负担，但不能区分检测模型、认字数量、预处理，也不能据此证明所有机器都是同一种原因。

### 风险一：退避可能降低特殊布局的及时发现能力

`lolhex/vision/scanbudget.py:28-30` 将自动冷却设为至少上次耗时的 4 倍，加长部分上限 120 秒。15 秒推理完成后至少等 60 秒才能再次自动整块扫描。标题位置正确的画面仍可走小标题检查；只能依赖整块定位的布局可能被拖后。按钮阴性、颜色未知不能作为永久停止兜底的依据。

### 风险二：耗时完成后可能发布已经过时的截图结果

`engine.py:578` 截图、`:582` 推理、`:563` 发布之间可以隔很久。`:637` 的对局状态保护能阻止离开对局后的发布，但没有以截图采集时间、窗口版本或卡片变化校验结果仍有效。若推理期间卡片已刷新、消失或窗口改变，代码存在短暂发布旧结果的路径。

这是代码可达风险，现有日志不能证明实际发生。按钮检测本身也不能解决在途结果过期；需要单独定义采集时间、窗口/会话版本、过期结果丢弃与重新检查规则。不能用推理结束时才创建的 Offer.at 代替真实截图采集时刻。

### 风险三：新检测器可能漏卡，颜色也不能代替存在性

现有 `detector.py:331-334` 会因卡框颜色与名字稀有度冲突而拒绝标题。`cardframe.py` 的谨慎阈值不能代替真实棱彩动画验收。按钮模板、卡框轮廓同样可能受遮挡、缩放、布局和版本影响。研究到的外部实现与阈值提供思路，不能证明适用于当前国服用户。

## 最小下一步

1. 先补一次扫描的采集、OCR 开始/结束、匹配与发布时刻，以及来源、输入尺寸、触发原因、检测/认字段耗时。标题路径同样需要限频计时，不能只给 full 增加细节。
2. 用有真实出现/刷新/消失标注的连续画面回放，区分“等待上一调用”“标题位置错误”“匹配/稳定确认拒绝”“推理本身慢”和“发布显示慢”；当前普通日志不足以完成这个区分。
3. 新增存在性检测先旁路计数，不影响当前识别结果；通过普通战斗负样本、棱彩动画、刷新、遮挡与失效校准验证后再参与调度。
4. 独立验证过期结果丢弃；决定兜底预算前比较原版、退避版和轻量检测版的尾部延迟、漏检与 CPU 开销。未通过时保留草稿，不把 Linux 单元测试当作实机性能验收。

本复核不否认用户观察到的延迟；它限制的是归因强度。在没有时间链与回放前，不能把“后台无效扫描”或“电脑配置”直接定为唯一原因。
