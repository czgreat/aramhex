# 1.1.5 装备采集交接需求

用户已确定：客户端使用我们服务器发布的最终资料，不选择自采或腾讯来源。服务器可以混合资料；发布前完成小样本筛选和推荐排序。先做全体英雄的核心三件套与命运之武器装备参考，不做六神装，不要求分段装备表，不要求自采加点。本文的 JSON 是结构示例，不是实际推荐，不能作为正式数据发布。

## 一、三件套

### 采集和统计

- 每个英雄最多展示 3 套，每套 3 件装备。有效候选不足 3 套就少给，不拿小样本补满。交付可以保留更完整的候选统计供复核，最终发布数组按推荐顺序排列。
- 优先评估能否获得前 3 件传说装备的实际完成顺序；默认不把鞋子、组件、消耗品当作三件套。请说明装备分类依据以及模式专属装备的处理。
- 若只能得到结算装备，只做无序组合；不能把装备栏位置、按 ID 排序、`legendary_items` 列表位置直接当成购买时间。无序组合用稳定键归并排列不同的同一组合；展示顺序由服务端指定。
- 若能获得实际购买记录，说明撤回、出售、重买、免费获得、自动升级、装备替换的处理。先交付一小批有对局证据的样例，核对后再批量统计有序三件套。
- 每个候选保留样本局数、胜场、胜率，以及选取率的分母。说明是“曾完成三件套”还是“结算仍持有三件套”，不要把两种口径混起来。每个英雄在一局里的统计单位、去重键、重连和重复抓取的处理要写清楚。
- 版本、模式、时间窗、区服口径必须一致；说明是否包含命运之武器等特殊海克斯样本。排名与样本门槛由采集/发布端确定并记录，不要求简单按原始胜率排序，客户端不再二次筛选或排序。

### 交付格式

采集端先交付 `core_builds.json`：英雄 ID → 已筛选、已排序的三件套数组。这是用于合包的中间文件，不是客户端新增下载文件。合包时写入现有英雄资料的 `heroes[英雄ID].builds.core`，其余加点、鞋子等资料继续由发布端保留或合成。

```json
{
  "17": [
    {
      "items": ["4645", "3135", "3089"],
      "ordered": false,
      "games": 10000,
      "wins": 5500,
      "win": 0.55,
      "pick": 0.10
    }
  ]
}
```

- ID 为字符串；`items` 必填。新交付的每套都明确写布尔字段 `ordered`：`true` 有购买顺序、显示箭头；`false` 无序组合、显示加号。
- `games`、`wins` 用整数，`win`、`pick` 用 0–1 小数；客户端三件套直接显示 `win`，不会从 `wins` 重算。发布端校验胜场不超过局数、胜率与计数一致。无胜负信息时省略 `win`，不能伪造数值。
- 当前 UI 只展示胜率和装备；局数、胜场、选取率用于复核和今后扩展。数组里的排序是最终推荐顺序，与 `win` 大小无关；`ordered` 只描述一套内部的购买先后。
- 缺少某英雄数据、需要保留腾讯组合等情况，由合包端明确决定；客户端不自行选择来源。不能靠普通单件装备榜拼出三件套。

## 二、命运之武器（海克斯 3081）

### 先核实样本含义

- 每个英雄展示最多 3 件单件装备参考，不是 3 套三件套；按服务端给定顺序显示。
- 必须使用该英雄选择命运之武器的对局，不能用普通英雄装备榜替代。
- 请先评估能否确认“实际被绑定/强化的装备”。“持有该海克斯且最终有某装备”的胜率，只能证明条件相关性，不能直接标成“该装备被强化时的胜率”。
- 前期曾核对 `legendary_items` 第一件与首次购买一致，但这不等于已经证明它就是实际绑定装备。请对选海克斯前已有装备、出售/撤回/重买、自动升级及巫师帽替换/转移等边界留出证据；不能确认的样本单独统计，避免混进已验证绑定口径。
- 能可靠确认第一件传说装备与绑定目标一致时，优先交付该目标的条件统计。若暂时不能确认，先交付可获得的字段、真实样例和限制说明，我们确定口径后再发布；不要凭猜测标注强化目标。
- `total` 是本英雄选择该海克斯的有效样本数；`games` 是该装备符合明确条件的样本数，`wins` 是其中胜场。若只是最终持有装备，比例不是互斥分布，不能称作强化目标占比；口径不清时先不发布该比例。

### 沿用现有客户端文件

交付 `hero_augment_items.json`：

```json
{
  "17": {
    "3081": {
      "source": "stats",
      "total": 10000,
      "items": [
        {"item": "4645", "games": 2000, "wins": 1100},
        {"item": "3135", "games": 1500, "wins": 900}
      ]
    }
  }
}
```

- `source: "stats"` 是现有“统计参考”的展示分类，不是客户端的数据源路由；无需新增自采/腾讯来源选择配置。
- `items` 已完成样本筛选并按最终推荐排序；客户端不按胜率重排，最多显示 3 件。胜率由客户端根据 `wins / games` 计算。
- 样本全部不够格时，可交付 `items: []` 和 `note: "样本太少，暂无装备参考"`；不强行补满。不需要重复提供装备名称和图标，前提是该 ID 已存在于我们发布的静态字典及本地图标包。
- 此文件加入公开统计包清单 `files`，带 SHA-256 和大小。它属于现有统计包，与三件套所在的英雄资料包走不同发布通道；软件只在对应三选一卡片出现时展示，暂不追踪玩家选中后装备变化。

## 三、两类数据共同交付的说明

- 统计版本、采样时间窗、模式、区服、去重规则、样本门槛、排名规则、覆盖英雄数、缺数据英雄、异常及排除清单，以及可复核的少量原始样例；原始对局样例留在受控位置，不放进公开资料包。
- 不要求采集 Agent 直接发布生产数据。先交付候选文件和统计报告；最终合包、校验与发布另走既有流程。
- `3040`、`3042`、`3121`、`2530` 这些自动升级形态，每次做新数据源都需向用户确认处理，不能擅自排除或合并到升级前装备；详见 `AUGMENT-ITEMS.md`。`2052`、`220013`、`3400` 不作为装备推荐。
- 新装备必须核对静态字典和本地图标。玩家模式不会为了补图标直接回源下载；不认识的装备可能只显示编号或文字，需要合包前处理。

## 四、发布和兼容性（由软件/发布端处理）

- 带显式 `ordered` 的三件套资料由候选工具自动要求 `min_client: "1.1.5"`。旧客户端会重排、并将无序组合也画成箭头，因此不能假设旧版已支持本协议。旧的 1.1.5 测试包同样没有这次改动，联调使用本次新测试包。
- 三件套所在的英雄资料包使用 `revision` 更新：相同版本、相同资料日期，只修改推荐顺序，也能通过新 revision 下发。资料日期不能倒退，不得把保留的旧腾讯资料冒充成新采集日期。
- 命运之武器所在的公开统计包支持同版本、同 `snapshot_at` 修订：每次发布递增 `seq`，并更新变动文件的 SHA-256 和大小。客户端在同快照下优先使用较大 `seq`，防止滞后镜像覆盖新修订；内置和缓存也按这一规则选择。只增加 `seq` 而内容相同会记录新序号，不反复下载。兼容旧包时允许相同 `seq` 的哈希修订，但服务器各镜像必须保证同序号同内容，不能依靠此兼容行为发布冲突的版本；不得伪造样本截止时间。
- 发版脚本 `scripts/update_data.py` 同样只从自有服务器取包，并按上述修订规则更新内置资料；支持 `--from` 读取已审核本地候选。CI 取不到时保留已提交的内置资料，正式发包前必须核对最终包内的版本、快照、`seq` 和文件哈希，不能把下载失败当作取得了最新包。
- 本次只改出装推荐的原序展示和三件套的顺序语义，六神装仍不展示，不新增分段装备，不更改海克斯评分、召唤师技能筛选和普通单件“常出装备”的规则。
