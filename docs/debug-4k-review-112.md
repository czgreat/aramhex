# 172 的 4K Debug 复核与 1.1.2 小修复

本轮读取 172 已运行的 `5bca02a` 便携测试版保存的文件，没有重启或覆盖玩家程序。测试在 235 独立目录离线运行；未改生产云控、服务端和正式发布渠道。

## 已确认的问题与修改

旧日志 2026-10-24 18:52:47.467 的整块识别结果为 `['死亡之舞', '', '死亡之舞']`，同一 ID `3079` 被当成左右两列，随后发布了推荐。接下来三轮标题读取均为空，浮层范围从常见的 `486,235 2896×1253` 变成 `652,30 2276×1268`。18:52:48.953 保存的截图已经是 Tab 计分板；截图晚于识别，不能把它当成原始 OCR 输入，也不能据此断言所有偏左问题均出于同一原因。

`scan_full` 现在在发布和校准之前拒绝“不足两个不同海克斯 ID”的选行。判断只遍历已有匹配，不增加截图、模型推理或扫描频率。仍保留两张不同卡片、第三张暂时不可读时的恢复能力。此修改只封住重复名字这一类错误；两个不同名字出现在非选卡界面的误报仍须继续排查。

另一个已确认的诊断缺陷是：识别完成后若因窗口变化丢弃结果，提前返回会漏记实际耗时。现在 `finally` 会补齐结束时间；过时识别仍不发布。普通日志的对局汇总增加重复名字拒绝次数，无需 `debug.txt`。

## 原始日志说明了什么

- 快照包含 142 张截图，其中 129 张为 3840×2160，13 张为 1920×1080 的选英雄画面。
- 10 个完整对局的 316 次整块扫描，对局平均耗时约 457—608 ms；40 条限频慢调用日志最大 1931 ms。此快照没有复现历史其他电脑的 20 多秒 OCR。
- 601 个可对齐的标题 OCR 批次：99 次读取三列、366 次读取一列、136 次读取两列。相邻短间隔内 90 次推荐内容变化均只改变一列。
- 8 次“三列都读取，但只一列内容变化”。例如 22:11:53.203、53.579，两侧 ID 未变，但指纹变化让两侧又读了一遍；不能把这些情况全解释为两张识别失败。保存图不是连续视频，尚不能判断具体哪些像素导致变化。
- 记录中始终是 3840×2160、DPI 144、Qt DPR 1.5，未发现真实 DPI 切换证据。Qt 的 2560×1440 逻辑坐标符合 150% 缩放，不能单凭这个比例认定分辨率错误。

## 测试与边界

Windows 235 完整回归 526 项通过（72.37 秒）；Linux 197 为 511 项通过、4 项跳过（25.19 秒）。新增 13 项 4K 状态测试覆盖单列刷新、两列读空后的恢复、负坐标屏幕、在途窗口移动、延迟校准写入和重复 ID 拒绝；另有 3 项过时扫描耗时测试。独立审查未发现两处产品修改的阻断问题。

状态测试中的 OCR 输出为脚本模拟，不能用来声称实战帧率、模型准确率和真实切屏全部通过。真实模型另在 235 回放原始截图的工作副本，原始 ZIP 保留不改；助手浮层只做近似遮罩。新旧结果相同不等于识别正确，动画、Tab、英雄选择须分别解释。

跨保存图的默认条带回放，只用于 OCR、缓存与确认逻辑压力检查：不同对局、数分钟间隔被压缩为每帧三个 0.31 秒观察，没有重建真实出现时间，不能据此计算端到端等待。另补充少量真实模型的完整识别→校准条带→缓存以及负坐标测试，仍属于静态图片回放。

现有循环在已确认校准读不到标题时，整块兜底的启动间隔可到 30 秒；默认校准则按 bootstrap 间隔扫描。这是可能的等待来源，与某次 OCR 本身计算很慢不同。本轮未擅自缩短全扫描频率，也没有重新引入此前撤回的自动退避；需要结合连续帧和总 CPU 开销再决定恢复策略。
