# 海斗助手识别方案源码对照（2026-10-24）

## 结论与适用范围

优先验证“轻量界面检测 → 标题定位 → 仅标题 OCR”的两阶段方案，而不是把延长整块扫描间隔视为最终修复。PR #15 早期退避降低重复计算，但不缩短一次昂贵推理，而且特殊未校准布局可能发现更晚；独立复核后已撤回，当前仅补诊断。

本次为固定提交的源码审阅，没有运行其他助手，也没有在本机或 235 做性能测试。外部项目的截图测试和速度数字不是 AramHex 的实测结果。下文检测器设计尚未实现；当前代码诊断范围见 performance-s1024.md，不改变云控或发布行为。

## 最值得借鉴的容错细节

Sygnano 的 [offer.rs](https://github.com/Sygnano/aram-mayhem-tracker/blob/7c28471bf5b511e545d8d1c38b63707157edb134/crates/mayhem-vision/src/offer.rs) 先查刷新按钮，再查隐藏卡片按钮，必要时才抓卡区。隐藏按钮可以在卡片收起时仍存在，不能单独等同于“三张标题可读”。按钮模板未匹配时仍允许定期卡框检测，避免模板过期后永远发现不了选项。

其 [vision.rs](https://github.com/Sygnano/aram-mayhem-tracker/blob/7c28471bf5b511e545d8d1c38b63707157edb134/apps/desktop/src-tauri/src/engine/vision.rs) 中无按钮兜底为 2 秒一次的卡框扫描，而非无条件大区域 OCR；标题不变也有 2 秒安全重读。指纹按单卡、按文字行局部比较，避免只刷新一张时变化被整组平均稀释。其“新读数为空时沿用旧值”的条件不能直接替换我们的两次真实观察确认，仍须防止刷新后遗留旧推荐。

其 [frames.rs](https://github.com/Sygnano/aram-mayhem-tracker/blob/7c28471bf5b511e545d8d1c38b63707157edb134/crates/mayhem-vision/src/frames.rs) 用缩小后的边缘轮廓判断存在性，避开卡片正文和容易被提示框遮挡的下部。作者记录过棱彩发光近白导致稀有度被误判为白银，因此后来通过识别出的名字查稀有度，不再由卡框颜色决定。

这不是我们已发生同一缺陷的证据，但应重点验证：我们的 `cardframe.py` 虽声明棱彩不确定时返回 None，仍存在灰白银色阈值；`detector.py::_read_strip` 会在像素分类与名字稀有度冲突时拒绝名字。没有真实棱彩序列时，不能证明白光帧绝不会落入 silver。**“返回 None”不等于“检测到没有卡片”；存在性与稀有度必须分开。** 颜色拒绝是否会漏掉正确结果也应有独立计数。

其 [paddle.rs](https://github.com/Sygnano/aram-mayhem-tracker/blob/7c28471bf5b511e545d8d1c38b63707157edb134/crates/mayhem-vision/src/paddle.rs) 对已定位标题直接认字，省去文本检测。我们已有对应的 `OCR.recognize(use_det=False)`，无需把这描述成新能力，也无需照搬其三线程推理方案。

## 我们真正需要补的部分

现有 `AugmentDetector` 已有默认标题位置、按列缓存、指纹、仅认字和两次新观察稳定机制。当前主要缺口是：正常战斗文字持续变化会导致标题区域缓存失效，且标题没匹配到时会周期性触发大区域“检测 + 识别全部文字”。缓存只能跳过不变的画面，不能替代“现在是否为选卡界面”的判断。

候选路径：

1. 已知窗口几何下，复用已有小条带；用独立的按钮/卡框轮廓给出 present、absent、unknown 三态证据，缓存缩放模板。先以只记录结果的方式运行，避免未经验证就阻断识别。
2. 有选卡证据时立即走现有标题 OCR 与稳定确认；按单列处理刷新，不等大区域冷却；尺寸改变后清理定位与旧结果。
3. 默认位置不可靠或证据 unknown 时，低频进行缩小画面的几何定位。找到疑似卡片后只识别候选标题；按钮阴性不是绝对否决，须有独立卡框检查。
4. 没有可靠定位仍保留受预算约束的整块兜底与手动重扫；模板失效、长期 unknown、标题失败分别计数。连续确定阴性可少做 OCR，但 unknown 不能永久沉默。
5. 检测到卡片消失时按现有发布规则清理旧结果；短暂遮挡、动画、隐藏/展开与刷新要分开，防止旧推荐“粘住”。

按钮和卡框检测的输入、像素量、耗时须先测，再确定轮询间隔。外部项目的 2 秒、0.35 分数或固定 70 像素边缘阈值不可直接当作国服验收参数。该方案保持画面识别路线，不依赖重新引入 LCU/2999。

## 新版本应补的 INFO 日志

在 PR #15 已补的 CPU/模型环境、慢调用阶段信息之外，按对局汇总以下计数；状态改变或超时才输出事件，不逐帧写日志：

- 来源：默认标题、校准标题、几何定位、大区域兜底、手动；每类次数、累计耗时、最大耗时与输入尺寸。
- 检测：present/absent/unknown、按钮与卡框分歧、模板/布局失效、跳过 OCR 次数；区分“画面没有卡”和“看不懂卡”。
- OCR：截图、预处理、检测、认字、匹配分段；全区域文本行数、标题成功数、颜色冲突拒绝数、指纹命中数与安全重读数。
- 状态：疑似出现、确认、单列刷新、收起、消失、校准变更与恢复；记录内部关联编号，统计首次疑似到推荐发布的延迟。

没有外部真实出现时刻或回放标注时，“首次疑似到发布”不能冒充玩家看到卡片到发布的端到端延迟。性能日志不写 OCR 原文；短期定向截图/原文需要客户端新增受控能力，旧云控点名不能补出原本没记录的内容。

## 正式合入的验证条件

先在空闲测试机做离线回放，覆盖真实国服白银/黄金/棱彩的连续动画、普通战斗负样本、鼠标提示遮挡、单张刷新与连续刷新、隐藏展开、首次未校准、失效校准、16:9/16:10/超宽与窗口缩放。截图集须保持原样，标注卡片出现、刷新、消失时刻。

按场景报告漏检、误触发、错误沿用旧卡、首次提示与刷新延迟的 p50/p95/最大值、CPU/墙钟时间及每分钟 OCR 次数。不能只测有卡静态图，不能只报告平均值。通过后再做真实 Windows 游戏负载验证，与原版和仅退避版比较。

Clarinet 的[验证记录](https://github.com/Clarinet-koiyun/hex-companion/blob/70c33d952ab4e7273307e9020b1ccf0f08dc34d0/docs/recognition-feasibility.md)也明确区分合成图、真实图缩放与实战：其有限回放速度不包含实战 GPU 争用或屏幕捕获，不能外推为我们的延迟承诺。

因此 1.1.2 的建议顺序是：补足诊断（已进入当前候选）→ 补真实回放集并验证颜色拒绝 → 评估轻量检测的旁路日志 → 达到验收条件才允许检测结果控制 OCR。未经验证的自动退避已从当前候选撤回。更换 OCR 后端、多线程推理和接口路线另做对照，不与此次修复一起扩大变更范围。
