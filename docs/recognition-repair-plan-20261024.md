# 识别延迟：从计算路径出发的独立修复方案

## 决策

独立子代理从算法工作量、库内部缩放、共享状态和调度四个角度复核后的建议：**先做可对照验证的“检测文字框 → 几何筛选标题候选 → 仅认候选”性能原型，再决定检测尺寸和是否需要并行。** 按钮/卡框只是辅助入口，不是完整修复。此文为设计，不表示性能原型已经实现或验收；当前 PR #15 仍是诊断候选。

代码证据：`AugmentDetector._scan_full` 在整个 BAND 上调用 `OCR.detect`，其实际参数同时启用 Det 和 Rec；返回所有文字后才字典匹配和挑同行。标题路径已经仅认字。慢对局的 full 与标题平均差异支持削减 full 工作量，但现有日志不能区分 Det、Rec、裁剪与其他处理分别占多少。

## 第一优先：减少一次 full 内不必要的认字

在 `lolhex/vision/ocr.py` 增加仅返回文字框的接口；在 `lolhex/vision/detector.py` 内先用文本框位置、高度、横向排列及候选标题区域筛选，再认有限候选，最后仍用原字典和稳定规则确认。这里的文字框检测与判断卡片存在的像素检测是两种不同工作。

首个原型保留一个模型实例和原线程数，不同时替模型或调匹配门槛，便于归因。几何候选先宽松：保留只有两个可读标题的情况、换行/长标题和默认位置不准时的广义定位恢复。候选上限与分级回退必须由真实回放确定，不能把原本需要 full 才能发现的布局硬性排除。

官方 `use_rec=False` 虽跳过 Rec，仍会 `detect_and_crop` 全部文字框，因此这一步主要省认字，不保证省掉 Det 和全部裁剪。若新分阶段日志显示 Det 占主导，应优先处理下一项，不承诺候选筛选就能根治。

## 第二优先：验证真实模型与实际推理尺寸

项目固定 rapidocr 3.9.2，中文初始化只覆盖线程；[官方 v3.9.2 配置](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/python/rapidocr/config.yaml)默认 Det/Rec 为 PP-OCRv6 small，不能直接套用其他助手 v4 mobile 的速度经验。实际打包配置、模型文件与新运行日志还须核实。当前候选已补模型族/大小/语言、检测缩放参数、Rec 批大小和形状的启动日志；这些是配置，不是每次模型实际张量尺寸，也不是模型文件哈希证明。

该版本还有两个缩放陷阱：

- [`DetPreProcess.resize`](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/python/rapidocr/ch_ppocr_det/utils.py) 的 min 模式会把短边不足的图放大，外层缩图可能被内部抵消。
- [`TextDetector.get_preprocess`](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/python/rapidocr/ch_ppocr_det/main.py) 在非 min 模式按输入长边选择 960/1500/2000，并不直接采用配置的 limit_side_len。因此简单设置 max+736 不足以证明模型输入被限制为 736。

性能原型须测实际送入模型的张量尺寸，比较缩放、候选数、文本框长宽比、Rec 批填充与耗时。只有同输入的 Det/Rec 分段数据才能决定缩检测输入、控制长框候选、改变批策略或替换模型。模型替换可能影响繁体、韩文和长标题准确率，也会影响打包/增量更新范围，单独做对照。

## 第三优先：让常态路径少进入 full，并保留恢复

按钮/卡框轮廓存在性检测先旁路计数，再验证是否可避免战斗背景无效 OCR。独立的 present/absent/unknown，阴性不能永久禁止恢复；模板变更、鼠标提示、棱彩发光、隐藏/展开和失效校准都须覆盖。优先复用现有按列缓存、指纹、仅认字和两次真实观察确认，不通过取消确认、放宽名字门槛换速度。

这解决“是否有必要启动昂贵调用”，不加速已在途调用，也不直接修正所有标题位置。不要再次把自动延长兜底间隔当作主要性能修复。

## 第四优先：只有必要时才拆任务

当前 full、标题和选人 OCR 共享 `OCR` 实例及锁。把 full 放进 worker 后，标题认字仍可能等同一把锁；[RapidOCR.__call__/update_params](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/python/rapidocr/main.py)还修改实例模式，不能简单去锁并发。复制完整模型则增加 CPU 和内存竞争，须考虑日志中已有内存分配失败历史。

`scan_full` 会修改校准、缓存和稳定状态，不能直接与标题检查并行共享 detector。若前面优化后仍有长任务，需将 full 计算改成不写共享状态的结果/校准提案，由拥有状态的线程按会话、窗口和采集版本验收。只保留最新待处理任务，不积压；定义过期丢弃和重新采样规则，而不是加一个固定短超时让慢电脑永远不能发布结果。在模型支持的调用边界调度，不能声称 Python 线程能随时中断一个 ONNX 推理。

## 本次已完成的确定修正

[`TextRecOutput`](https://github.com/RapidAI/RapidOCR/blob/v3.9.2/python/rapidocr/ch_ppocr_rec/typings.py) 的耗时字段为 elapse，完整输出才有 elapse_list。当前候选已兼容仅认字返回类型，避免真实标题认字阶段一直记 unknown；未执行检测不伪造零耗时。另补模型配置启动日志。都不改变扫描决策。

## 下一步验收

先在空闲测试机，用同一批有出现/刷新/消失标注的真实连续图，对比原版和有限候选原型：首次提示、单卡刷新 p50/p95/最大延迟、漏检、误识别、旧结果残留、CPU、内存及实际模型张量尺寸。覆盖普通战斗负样本、白银/黄金/棱彩动画、遮挡、首次/失效校准、16:9/16:10/超宽及缩放。之后再做 Windows 实际游戏负载验证。

诊断单元回归仅能证明日志/逻辑，不证明性能收益。未获得真实画面前，不把该设计写成已修复，也不把其他助手的耗时数字作为我们的承诺。
